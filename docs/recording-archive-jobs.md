# Recording archive jobs

The recording download button starts an authenticated background job, polls progress, then submits a native browser POST with a two-minute job-specific capability. No full-archive Blob is buffered by JavaScript. The button is disabled during preparation, and briefly across the native handoff to absorb double clicks; after handoff the browser owns transfer progress. Errors are visible and retryable.

`POST /archiveJobs` accepts `search` as form data. `GET /archiveStatus?id=...` returns `queued`, `building`, `ready`, or `failed`, plus progress. Both require existing Core authentication. Ready responses include a short-lived ticket. `POST /archiveFile` accepts only a valid job ID and HMAC ticket and serves that ready archive; no arbitrary path is accepted. Legacy `GET /downloads?search=...` now returns job JSON rather than blocking on archive construction. Non-browser clients must poll status and then submit the ticket.

Jobs are scoped to identity, captured server ACL and filters. JWT context is normalized to Core user_name/session_id/role. The worker applies captured ACL to both call selection and detail records, retains onlyEmployeeConversations filters, skips report totals and bounds call selection. Duplicate recording paths are archived once. Existing file validation and archive size/count limits remain.

At most eight jobs may be queued/building, with one archive builder at a time. A build gets 30 minutes after acquiring the global lock; queue waiting does not consume this timeout. Duplicate requests join an active task. Worker locks prevent duplicate builders and allow interrupted jobs to become visible failures. Failed jobs may be retried.

Ready results are cached for 15 minutes outside the module's legacy five-minute temporary-file cleaner, under core.tempDir/ModuleExtendedCDRsArchiveJobs. CDR/module/group DB file metadata forms a conservative cache revision; unrelated database writes may invalidate reuse. Recording inode, size, mtime and ctime are also checked before reuse and transfer. Thus active tasks represent a request-time selection; later requests can obtain new data after source changes. Cache maintenance evicts expired/older ready files above 4 GiB on the next maintenance pass. An in-flight archive can temporarily add up to the existing 2 GiB archive limit. Five-minute cron maintenance holds locks and removes abandoned partial archives. A bounded pool of persistent lock files prevents unlink/recreate races.
